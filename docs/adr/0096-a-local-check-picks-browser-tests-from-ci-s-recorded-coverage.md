# A local check picks browser tests from CI's recorded coverage

2026-11-24 (mattpocock/cookout#444). [The local check runs only the browser tests a branch reaches](0092-local-check-runs-only-the-browser-tests-a-branch-reaches.md), but it found them through the module graph, and browser tests reach the cookout through the page it serves, not through imports. So a branch changing any view ran every browser test, and most UI tickets saved nothing. This follows up Matt's decision on the board (thread 3416, msg 3626) that a local `pnpm check` runs only the browser tests a branch affects.

## Decision

- Each shard of CI's `browser` job runs its browser tests through `pnpm browser:coverage` (`scripts/browser-coverage.ts`), which turns on `scripts/browser-coverage-recorder.ts` from `playwright.config.ts`. The recorder starts V8 JS coverage on every page a test opens and takes it before the page, its context or the worker's browser closes. Each page's coverage is mapped through the source map Vite serves inline back to the app source files, as each file's functions (first and last line) and which of them ran (`scripts/lib/page-coverage.ts`).
- When every browser test passed, the script merges the pages into one coverage map, `.browser-coverage/map.json`: the commit it ran at, each loaded file's functions, and for each browser test the functions it called in each file (`scripts/lib/browser-coverage.ts`). A test some of whose pages it couldn't record (a page it didn't start coverage on, a page closed or a worker ended before its coverage was taken, a file served with no source map) is left out of the map. If coverage was recorded outside any test, or Playwright's instrumentation hooks are missing, no map is made. The map is generated, never written by hand.
- Each shard of the `browser` job writes its own map, with the shard (`1/3`) and the tests it couldn't record all of, and uploads it as the `browser-coverage-map-<shard>` artefact (`scripts/lib/coverage-shards.ts`). That is the only workflow change: one `actions/upload-artifact` step, no new secret and no new permission. A run's maps are merged only when every shard's map is there at the same commit, and a test any shard couldn't record all of is left out.
- A full local `pnpm check` fetches the newest map CI recorded on a commit that is an ancestor of the branch's merge base with `origin/v1`, with the `gh` the agent already uses (`gh api …/actions/artifacts?name=browser-coverage-map-1`, then `gh run download --pattern 'browser-coverage-map-*'` for that run), and keeps it under the git common directory, keyed by that merge base, so the worktrees on a machine fetch it once per v1 commit (`scripts/lib/coverage-map-fetch.ts`). It fetches only when the branch changes a file of the served app.
- The module graph still decides everything outside the served app, as before. A changed file only `app/web.tsx` reaches (the app the browser runs, not the server) is looked up in the map: for each changed hunk (the lines `git diff -U0 --merge-base origin/v1` shows as changed on the base's side, or the two lines either side of an insertion), the innermost function whose body holds the hunk decides. The browser tests that called that function run. A hunk inside no function's body (an import, a top-level constant, a function's first or last line) runs every browser test that loaded the file. Browser tests the map doesn't hold run too.
- It fails safe, as before, and runs every browser test, saying why on stderr: when there is no map (no `gh`, no network, no map from a commit on the base), when the changed file differs between the map's commit and the branch's merge base (the map is stale for it), when the map doesn't hold the file (a new file), when git shows no changed lines for it, and when a changed file is one the cookout server reaches (`app/dev.ts` or `scripts/browser-test-server.ts`), since the server's coverage isn't recorded.

## Why

The coverage is per test file because Playwright runs a file's tests in one worker and the map is read per file. Function-level coverage, not line-level, decides because every app module is imported on every page, so a module's top level runs in every test; a function only runs in the tests whose pages rendered or called it. Taking the innermost function around a hunk, and every test that loaded the file for anything outside a function's body, means a change to a top-level line or a function's signature never skips a test that could see it.

Committing the map and checking it with a drift check was the other choice. It would have to be regenerated by running every browser test whenever any view changes, which is the run this saves, and every concurrent UI ticket would conflict on it. Fetching it from CI keeps the map exactly as CI recorded it.

## Consequences

CI's browser job runs a little slower with coverage on. An unsharded CI browser run doesn't record coverage, since every browser test with coverage on didn't fit in one job's five minutes. A local check now makes one `gh` call per v1 commit a machine hasn't seen when a branch changes a view, and a green local `pnpm check` still doesn't promise every browser test passes: CI runs every one before anything lands on v1.

The recorder relies on Playwright's internal client instrumentation (`_instrumentation.addListener`, the hooks Playwright's own tracing uses). If an upgrade removes it, CI makes no map and local checks run every browser test.

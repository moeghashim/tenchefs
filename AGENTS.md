# AGENTS.md

The cookout: a self-hosted, Slack-style board for people and agents. Spec: mattpocock/cookout#1.

- [GLOSSARY.md](GLOSSARY.md): the domain language. Names in code use its terms.
- `pnpm check` runs, through `scripts/check.ts`, what the change since origin/v1 reaches; the script decides, not you ([ADR](docs/adr/0113-a-local-check-runs-only-what-the-change-reaches-and-never-repeats-the-hook.md)). Commit with `scripts/commit.sh`, run `pnpm check` once after your last commit, and it must end `RESULT: PASS`; run `pnpm check --all` only to run everything on purpose. Locally, without `--all` or `--job`, it runs knip, the drift checks (validators, hygiene, docs, api, exports, render), fixers and canaries, the unit tests whose imports reach a changed file (`vitest related`, without the coverage thresholds), and the browser tests the branch reaches ([ADR](docs/adr/0092-local-check-runs-only-the-browser-tests-a-branch-reaches.md)), picked for a change to the served app (a view) from the coverage map the Release workflow's browser jobs record and the check fetches with `gh`, all of them when there is no map or it is stale ([ADR](docs/adr/0096-a-local-check-picks-browser-tests-from-ci-s-recorded-coverage.md)). It doesn't run lint, format, types or seams, since the pre-commit hook ran them on every commit. A change to a file on one list in `scripts/lib/test-selection.ts` (the root configs, the lockfile, the testing module, and the test environments, servers and containers under `scripts/`) runs every unit and browser test, with one stderr line naming the file; a docs-only change (`*.md`, `docs/`, `.changeset/`) runs no tests. `--all` runs every check and every test, and every CI call passes it. Before its verdict it prints a `skipped:` line for the e2e suite, one naming lint, format, types and seams as the pre-commit hook's, and one each for the unit and the browser tests it didn't select; `pnpm test` and `pnpm browser` run them all. The e2e suite (`packages/e2e` on the Docker image) runs only on CI, as the Check workflow's `e2e-docker` job and again as Release's ([ADR](docs/adr/0132-check-runs-the-e2e-suite.md)); run it on purpose with `pnpm e2e:docker`. The Check workflow runs on pushes to `v1`, on pull requests into v1 and on `workflow_dispatch`, never on `ticket-*` pushes, with 9 jobs: `static` (lint, canaries, types, fixers, seams, knip, format and drift, one step each, stopping at the first that fails), `tests` ×6 (each running the files that give it a sixth of the test time the newest earlier Check run recorded, `scripts/lib/timed-shards.ts`), `coverage` and `e2e-docker` (`pnpm e2e:docker`, both legs, in parallel with the others), so a worker's own `pnpm check` is the check before a pull request ([ADR](docs/adr/0105-check-runs-8-jobs-only-on-v1-and-merge-ticket-branches.md)). On a pull request into v1 it runs those 9 on GitHub's merge with v1 plus `browser` ×6, Release's browser shards from the reusable `.github/workflows/browser.yml`, each running only its share of the browser tests the change reaches, picked from Release's coverage map by `node scripts/check.ts --job=browser --reached`; a docs-only change runs none ([ADR](docs/adr/0119-a-pull-request-into-v1-runs-check-with-the-browser-tests-it-reaches.md)), and last, once every other job has ended, `adr-numbers`, which fails when an ADR the change adds takes a number the latest origin/v1 already gives another, naming the free one, so two pull requests whose Checks ran side by side can't both land the same number ([ADR](docs/adr/0139-a-pull-request-s-check-ends-by-checking-its-adr-numbers-against-the-latest-v1.md)). The Release workflow is the gate ([ADR](docs/adr/0114-release-is-the-gate-on-the-newest-green-v1-commit.md)): it runs on its own when Check completes on v1, going ahead only when the newest green v1 commit isn't deployed, something user-facing (not docs, tests, `scripts/` or `.github/`) changed since the newest `deploy/*` tag, and no Release gate run started in the last 30 minutes, or else printing one line saying why and ending green, except that when nothing user-facing changed and main lacks the commit, it only moves main to it, with no gate or deploy ([ADR](docs/adr/0123-release-moves-main-for-a-commit-with-nothing-user-facing.md)); when a gate run under 30 minutes old is the only reason, it waits until that run is 30 minutes old and chooses and decides again, as it has no schedule ([ADR](docs/adr/0121-release-waits-out-the-gate-spacing-instead-of-a-schedule.md)); a `workflow_dispatch` on v1 always goes ahead (`scripts/lib/release-go.ts`). It picks the newest v1 commit whose Check push run is green, or, for v1's head only, whose newest Check run is a green `workflow_dispatch` run such as the Red v1 workflow starts after a revert ([ADR](docs/adr/0129-release-counts-a-dispatched-check-on-v1-s-head.md)) (`scripts/release-commit.ts`, printing why it skipped each newer one), runs `browser` ×6, pack smoke, the published client and `e2e-docker` on it, and only when all pass fast-forwards main to it, calls Deploy and runs changesets, first adding a patch changeset when shipping code landed since the last version with none (`scripts/release-changeset.ts`), whose Version Packages pull request is against v1; its `dry-run` input only prints what it would publish and deploy. `pnpm check` refuses a change that loosens the lint config (in `.oxlintrc.json` a rule turned off or downgraded, an added or widened override or an added ignorePatterns entry; an added entry in `docs/lint-opt-outs.md`; any change to `.dependency-cruiser.cjs`), naming the file and the hunk, and refuses what it can't tell tightens; a new rule, its own owner exemption or a `warn` made `error` passes. Its drift job judges the change against the merge base with origin/v1 locally, and the push's range on v1's Check ([ADR](docs/adr/0109-the-lint-config-guard-runs-in-the-check-and-approval-is-a-commit-trailer.md)). Only Matt approves a loosening: the commit that makes it carries the trailer `Lint-approved-by: board msg <id>`, naming his message. With a clean working tree (nothing uncommitted or untracked) and a green push Check run at HEAD (only on `v1`), it runs nothing and prints `RESULT: PASS (CI green at HEAD <run url>)`; when `gh` is missing or fails it says so in one line and runs everything, and `--all`, `--ci` and `--job` runs never skip. Its last line is its verdict, after any time budget warnings: `RESULT: PASS` or `RESULT: FAIL (<failed checks>)`. On a failure, the lines just before the verdict are `Failures:` and then the check, file and name of each failing test and the check, `file:line` and rule of each lint violation, at most 20 of each and then `…and N more`. It waits while another `pnpm check` or `pnpm coverage:changed` runs on the machine, printing one line on stderr that names the worktree it waits for (CI doesn't wait). Its first line is the machine's 1-minute load average and core count; when the load is above the core count it warns on stderr, since browser tests then time out at random.
- A changeset (`pnpm changeset`) is optional: write one only when a change has something to tell users of `@ai-hero/cookout`. No check asks for one.
- `pnpm coverage:changed` runs the tests and lists, as `file:line`, every uncovered line or branch in files changed against v1. Run it before `pnpm check` to catch a coverage gap early. It waits for the same machine-wide lock as `pnpm check`. Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed step>)`, the step being `tests` or `uncovered lines`.
- Land your own pull request by these steps, with no review and no merge queue ([ADR](docs/adr/0127-a-worker-lands-its-own-pull-request-after-its-pull-request-check-is-green.md)):
  1. Commit with `scripts/commit.sh`.
  2. Run `pnpm check` after the last commit. Its last line must be `RESULT: PASS`.
  3. Push the branch, and open the pull request against v1 (`gh pr create --base v1`) if it isn't open yet.
  4. `git fetch origin v1`, then `git merge --no-edit origin/v1`.
  5. On a conflict, resolve it: for a generated file, rerun its generator (`pnpm validators`, `pnpm api:write`, `pnpm lint:baseline`); in a migrations list, keep v1's entries first and yours after them; in Vitest's coverage thresholds, keep the lower number. Commit with `scripts/commit.sh`, run `pnpm check` again, and go back to step 4.
  6. With no conflict, `git push`, then wait for the pull request's Check run to be green: `gh pr checks <PR> --watch --fail-fast`, its exit code unpiped. If it's red, fix the failure, commit with `scripts/commit.sh`, run `pnpm check` and go back to step 4; never merge while a job is red or running. When it's green, `gh pr merge <PR> --merge`. If GitHub refuses because v1 has moved and now conflicts, go back to step 4. Making that check required is a repository setting, which agents never change.
  7. Close the ticket's issue: `gh issue close <N> --comment "Landed on v1 in <merge commit SHA>"`, with the SHA from `gh pr view <PR> --json mergeCommit --jq .mergeCommit.oid`.
  8. Don't wait for v1's Check run. You're done.

  A clean `git merge` of v1 makes its commit without the pre-commit hook, and v1's Check covers the merged result. If a red v1 follows, a fix-forward ticket goes first, and it lands by the same steps.
- On a red v1, the Red v1 workflow reruns the red run's failed jobs once; if the rerun is red too, it opens one fix-forward issue (`v1 is red: <failed jobs> since <short sha>`), which goes first in line, and closes it when v1 goes green. If v1 has no green Check run 30 minutes after the first red commit's red run, it reverts that commit on v1 and comments on its pull request ([ADR](docs/adr/0128-a-red-v1-is-reverted-after-30-minutes.md)). If your merge is reverted, the reverted pull request says so. Reopen the ticket, fix the cause on your branch, and land again by the landing steps.
- `pnpm ci:wait` waits for the Check push run of HEAD (on a `ticket-*` branch there is none, so it fails once it has waited 10 minutes for one), polling every 30 s, prints each job's conclusion and each failed job's failed steps, then each failing Vitest or Playwright test in its log (file, name and the first lines of its error), then its last 20 log lines, and exits 0 only if every job passed (a job that failed only on a time budget warns). Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed jobs>)`. It judges the commit, not one run: the commit is green if any completed run on it succeeded, a cancelled run never counts as red, and if every run on it was cancelled it reruns the newest once. A job cancelled after running for about its `timeout-minutes` in `.github/workflows/check.yml` was cut off at its time limit, not superseded: then it names each such job and its limit, doesn't rerun, and exits 3 (other failures exit 1), with `RESULT: FAIL (<jobs> cut off at its time limit)`. `pnpm ci:wait --sha <sha> --branch v1` watches a merge on v1. Use it to wait for CI; never hand-write `gh run watch`, and never pipe a watch, since a pipe hides its exit code.
- `pnpm budgets` reports each stage's wall-clock budget against the median of its last 10 runs: pre-commit 2 s, the worker's `pnpm check` 2 min, landing 30 s, v1 Check 3 min, Release gate 6 min, landed to live 30 min (#639). `scripts/commit.sh` records how long its `git commit` took, and a local `pnpm check` (without `--all` or `--job`) its wall time, in `stage-times.log` in the git common directory, shared by every worktree on the machine; recording never fails or slows them. The GitHub stages come from `gh`: landing from a pull request's head (its merge of v1) to its merge into v1, v1 Check as the duration of v1's Check push runs, the Release gate from its run's start to the end of its last gate job, landed to live from a pull request's merge to the first `deploy/*` tag containing it. A stage with fewer than 10 runs, or whose data can't be read, says so and isn't judged. Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<stages> over budget)`. It runs in no workflow and fails no other run. An over-budget stage is a defect ticket, first in line; it is never a failure on time alone.
- `pnpm lint:changed` runs the hook's lint (same rules and baseline ratchet) and type check on files changed against origin/v1, staged, unstaged or untracked, without committing or fixing, then `pnpm knip` on the whole repo, so an unused export, file or dependency fails here with knip's report rather than after the tests in `pnpm check` or on the pull request's Check run. It prints each new violation once, in the hook's format (including ones the hook would fix for you), and exits non-zero if there are any. It ends with a summary by rule: each failing rule's count and its first violation, most frequent first, capped at 40 lines. Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed checks>)`, the checks being `lint`, `types` and `knip`. Run it while you work to see lint early.
- Don't run fix, format or other lint commands yourself. Commit, and the pre-commit hook fixes and formats what you staged, judging the lint on the formatted text, as `lint:changed` does; then fix by hand only what it prints as left over: each new violation once, as `file:line rule message`, then "N new violations in M files". Commit with `scripts/commit.sh`, which takes `git commit`'s arguments: lefthook skips the whole hook when nothing is staged, so it fails then with "nothing staged: run git add first".

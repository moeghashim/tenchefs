# AGENTS.md

The cookout: a self-hosted, Slack-style board for people and agents. Spec: mattpocock/cookout#1.

- [GLOSSARY.md](GLOSSARY.md): the domain language. Names in code use its terms.
- `pnpm check` runs the checks CI runs through `scripts/check.ts`, browser tests included. The e2e suite (`packages/e2e` on the Docker image) runs only on CI, as the Release workflow's `e2e-docker` job before it publishes ([ADR](docs/adr/0088-the-e2e-suite-runs-only-on-ci.md)); run it on purpose with `pnpm e2e:docker`. Pack smoke and the published client run only there too. The Check workflow runs on pushes to `v1` and `merge-ticket-*` only, never on `ticket-*` pushes or pull requests, with 8 jobs: `static` (lint, canaries, types, fixers, seams, knip, format and drift, one step each, stopping at the first that fails), `tests` ×3, `browser` ×3 and `coverage`; the merge-ticket run is the gate, so a worker's own `pnpm check` is the check before a pull request ([ADR](docs/adr/0105-check-runs-8-jobs-only-on-v1-and-merge-ticket-branches.md)). Run `pnpm check` once before you finish; it must exit 0. `pnpm check` refuses a change that loosens the lint config (in `.oxlintrc.json` a rule turned off or downgraded, an added or widened override or an added ignorePatterns entry; an added entry in `docs/lint-opt-outs.md`; any change to `.dependency-cruiser.cjs`), naming the file and the hunk, and refuses what it can't tell tightens; a new rule, its own owner exemption or a `warn` made `error` passes. Its drift job judges the change against the merge base with origin/v1 locally, and the push's range on v1's Check ([ADR](docs/adr/0109-the-lint-config-guard-runs-in-the-check-and-approval-is-a-commit-trailer.md)). Only Matt approves a loosening: the commit that makes it carries the trailer `Lint-approved-by: board msg <id>`, naming his message. With a clean working tree (nothing uncommitted or untracked) and a green push Check run at HEAD (only on `v1` or a `merge-ticket-*` branch), it runs nothing and prints `RESULT: PASS (CI green at HEAD <run url>)`; when `gh` is missing or fails it says so in one line and runs everything, and `--ci` and `--job` runs never skip. Before its verdict it prints one `skipped:` line naming the e2e suite. Locally it runs only the browser tests the branch reaches, and runs them all when it can't tell ([ADR](docs/adr/0092-local-check-runs-only-the-browser-tests-a-branch-reaches.md)); CI runs them all. For a change to the served app (a view) it picks them from the coverage map CI's browser job records and the check fetches with `gh`, and runs them all when there is no map or it is stale ([ADR](docs/adr/0096-a-local-check-picks-browser-tests-from-ci-s-recorded-coverage.md)). When every file changed against origin/v1 is docs (`*.md`, `docs/`, `.changeset/`, deletions included), it skips the tests and browser jobs and says so in one line; the rest (docs drift, format and so on) still runs, and CI still runs everything. When it skips some, a second `skipped:` line names them; `pnpm browser` runs them all. Its last line is its verdict, after any time budget warnings: `RESULT: PASS` or `RESULT: FAIL (<failed checks>)`. It waits while another `pnpm check` or `pnpm coverage:changed` runs on the machine, printing one line on stderr that names the worktree it waits for (CI doesn't wait). Its first line is the machine's 1-minute load average and core count; when the load is above the core count it warns on stderr, since browser tests then time out at random.
- `pnpm coverage:changed` runs the tests and lists, as `file:line`, every uncovered line or branch in files changed against v1. Run it before `pnpm check` to catch a coverage gap early. It waits for the same machine-wide lock as `pnpm check`. Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed step>)`, the step being `tests` or `uncovered lines`.
- `pnpm merge-ticket <N>` merges ticket-N into v1 by fast-forwarding v1 to a green merge-ticket-N ([ADR](docs/adr/0104-v1-moves-only-by-fast-forward-from-a-green-merge-ticket-branch.md)); a merge queue isn't available on this user-owned repository. If it stops on a conflict, resolve it and commit on merge-ticket-N, then run `pnpm merge-ticket <N> --continue`: it checks and pushes. If origin/v1 has moved past merge-ticket-N's v1 parent, `--continue` first merges the new v1 into merge-ticket-N, so never merge v1 into it by hand; it prints which of the two it did. Its local check is only the fast ones (types, lint and hygiene, which holds the migration and ADR guards); CI is the merge's full check. It pushes the merge to a branch named for its commit, `merge-ticket-N-<first 12 hex of the SHA>`, with a plain push, never forced (or, if origin already has that branch, doesn't push it again), deleting any earlier attempt's merge-ticket-N branches, which closes their pull requests; it opens or reuses a pull request from that branch → v1 titled `Merge ticket-N: <title> (#N)`, for review and links, and never asks GitHub to merge it. It waits for that branch's Check run on that exact SHA, and only when every job is green runs `git push origin <sha>:refs/heads/v1`, never forced, which GitHub shows as the pull request merged; then it deletes the pushed branch. If the push is refused because v1 moved, it merges the new origin/v1 into merge-ticket-N (through the same guards and fast checks), pushes and waits for the new commit's run, and pushes again, printing each round, up to 5 rounds; it stops on a conflict with the moved v1, so resolve it and run `--continue`. If merge-ticket-N's run is red, it stops and prints the failed jobs, ending `Nothing was pushed to v1.`, and leaves the pushed branch on origin. A flaky job is retried once: every merge-ticket-N run is waited on until it finishes, then get their failed jobs rerun once (`gh run rerun <id> --failed`), and the rerun is judged, so a rerun never needs a new commit. A red run names the commit it ran on. A job skipped because a job it needs failed isn't named as failed; a skipped job blocks only when every other job passed. Never rerun a job by hand. Before its check, it runs `pnpm install --frozen-lockfile` if the merged `pnpm-lock.yaml` differs from ticket-N's. It reads no ticket-N Check run, as Check doesn't run on `ticket-*` pushes. It refuses to merge while v1's latest Check run has a job that is not green, waiting for a run still in progress, except that a v1 run in progress or cancelled on a commit already green on a `merge-ticket-*` branch counts as green, and a run cancelled by a newer push is judged by that newer run; only the ticket that fixes a red v1 passes `--fixes-red-v1`. It refuses a merge whose migrations list doesn't begin with origin/v1's, entry for entry; only a ticket that moves a migration production hasn't run passes `--reorders-undeployed-migrations`, which compares with the newest `deploy/*` tag instead. It runs `pnpm check`'s lint-config guard on ticket-N against its v1 merge base; `--approved=<board msg id>` passes it and records the trailer on merge-ticket-N's merge commit. Its last line is its verdict: `RESULT: MERGED <sha>` after the fast-forward push, or `RESULT: FAIL (<failed step or jobs>)`. A job of any run cut off at its time limit it reports as `ci:wait` does: it names the job and its limit, doesn't rerun it (not on `--continue` either), and exits 3, with `RESULT: FAIL (<branch>'s Check run: <jobs> cut off at its time limit)`. After the push it prints v1's new SHA and exits 0, without waiting for v1's own push run of that already-green commit.
- `pnpm ci:wait` waits for the Check push run of HEAD (on a `ticket-*` branch there is none, so it fails once it has waited 10 minutes for one), polling every 30 s, prints each job's conclusion and each failed job's failed steps, then each failing Vitest or Playwright test in its log (file, name and the first lines of its error), then its last 20 log lines (merge-ticket's red report prints the same), and exits 0 only if every job passed (a job that failed only on a time budget warns). Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed jobs>)`. It judges the commit, not one run: the commit is green if any completed run on it succeeded, a cancelled run never counts as red, and if every run on it was cancelled it reruns the newest once; merge-ticket's waits do the same. A job cancelled after running for about its `timeout-minutes` in `.github/workflows/check.yml` was cut off at its time limit, not superseded: then it names each such job and its limit, doesn't rerun, and exits 3 (other failures exit 1), with `RESULT: FAIL (<jobs> cut off at its time limit)`. `pnpm ci:wait --sha <sha> --branch v1` watches a merge on v1. Use it to wait for CI; never hand-write `gh run watch`, and never pipe a watch, since a pipe hides its exit code.
- `pnpm lint:changed` runs the hook's lint (same rules and baseline ratchet) and type check on files changed against origin/v1, staged, unstaged or untracked, without committing or fixing, then `pnpm knip` on the whole repo, so an unused export, file or dependency fails here with knip's report rather than after the tests in `pnpm check` or on merge-ticket-N's Check run. It prints each new violation once, in the hook's format (including ones the hook would fix for you), and exits non-zero if there are any. It ends with a summary by rule: each failing rule's count and its first violation, most frequent first, capped at 40 lines. Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed checks>)`, the checks being `lint`, `types` and `knip`. Run it while you work to see lint early.
- Don't run fix, format or other lint commands yourself. Commit, and the pre-commit hook fixes and formats what you staged; then fix by hand only what it prints as left over: each new violation once, as `file:line rule message`, then "N new violations in M files". Commit with `scripts/commit.sh`, which takes `git commit`'s arguments: lefthook skips the whole hook when nothing is staged, so it fails then with "nothing staged: run git add first".

- Only Matt approves a domain term. A term counts as approved only with a dated decision of Matt's cited next to it, in an ADR under `docs/adr/` or a comment on a mattpocock/cookout issue; without one it stays proposed.
- In a git worktree, create files with the Write tool (not `cat > … <<EOF`), run every command from the worktree root, and add root dependencies with `pnpm add -w`.
